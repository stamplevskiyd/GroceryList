# ADR-0010. Аутентификация: свой OAuth AS на FastAPI, `mcp` SDK как resource server, PAT, cookie-сессии

Статус: принято · Дата: 2026-09-29

## Контекст

Три вида клиентов (спец. §2, §6):

- PWA в браузере;
- MCP-клиенты с OAuth — claude.ai, Claude Desktop и мобильное приложение, Claude Code, ChatGPT;
- MCP-клиенты, которым удобнее статический токен — Codex CLI, скрипты.

Внешнего IdP в v1 нет; бэкенд сам — Authorization Server (AS).

Актуальная спецификация авторизации MCP — **2026-07-28**:
- регистрация клиентов через Client ID Metadata Documents (CIMD) — SHOULD;
- Dynamic Client Registration (DCR) — MAY и объявлен устаревшим;
- `resource` (RFC 8707) и проверка аудитории токена — MUST;
- `iss` в ответе авторизации (RFC 9207) — SHOULD, в будущем MUST.

Поведение клиентов:
- **Claude** поддерживает DCR и CIMD. CIMD выбирает, только если метаданные AS содержат
  `client_id_metadata_document_supported: true` и `"none"` в `token_endpoint_auth_methods_supported`.
- **Claude Code** использует loopback-redirect со случайным портом.
- **ChatGPT** использует CIMD, только если AS поддерживает `iss`.

Библиотеки (сентябрь 2026):
- `mcp` 2.2 (`MCPServer`) и FastMCP 4.0 умеют быть собственным AS, но их встроенный AS не
  поддерживает CIMD и `iss`, а в метаданных жёстко нет `"none"` — клиенты будут откатываться
  на устаревший DCR;
- документация SDK не рекомендует встроенный AS для новых серверов.

## Решение

### Разделение ролей

- **MCP-сервер — официальный `mcp` 2.x в роли resource server:**
  `MCPServer(token_verifier=GroceryTokenVerifier(), ...)`, встроенный AS SDK не используется.
- **OAuth AS — собственные маршруты FastAPI** в модуле `auth`, логика — в сервисе `auth`
  (ADR-0008), таблицы — наши (спец. §4).

### MCP-часть

- **Верификатор** — один на все Bearer-токены:
  - префикс `gl_pat_` → поиск PAT по хешу;
  - иначе → поиск access token по хешу в `oauth_tokens`, проверка срока, отзыва и `resource`
    (равен канонному URL MCP-сервера, `AuthSettings.validate_token_resource=True`).
  - Возвращает `AccessToken`: `subject = user_id`, в claims — `client_id` и `client_name`.
    Для PAT — `resource` = наш URL.
- **Middleware `MCPServer` на `tools/call`** — общая обёртка из ADR-0003/0004/0012:
  1. открывает `unit_of_work()`;
  2. загружает пользователя по `get_access_token().subject` и выставляет его в контекст;
  3. строит `McpSource` из claims (`get_mcp_source()`);
  4. переводит `DomainError` в `ToolError` с текстом для модели.
- Невалидный токен → 401 с `WWW-Authenticate: Bearer resource_metadata="…"`
  (SDK формирует сам).
- **Встраивание в FastAPI:**
  - `streamable_http_app()` монтируется последним на `/`, внутренний путь — `/mcp`
    (иначе редирект `/mcp` → `/mcp/`);
  - lifespan FastAPI сам входит в `mcp.session_manager.run()` — lifespan смонтированного
    приложения не выполняется;
  - `transport_security` — `allowed_hosts` / `allowed_origins` из `settings.app.public_url`
    (иначе 421);
  - CORS разрешает `Authorization` и `Mcp-*`, отдаёт наружу `Mcp-Session-Id` и `WWW-Authenticate`.

### OAuth Authorization Server

- **Метаданные** `/.well-known/oauth-authorization-server`:
  - `code_challenge_methods_supported: ["S256"]`;
  - `token_endpoint_auth_methods_supported: ["none"]` — все клиенты публичные;
  - `client_id_metadata_document_supported: true`;
  - `authorization_response_iss_parameter_supported: true`;
  - `registration_endpoint`, `revocation_endpoint`;
  - `scopes_supported: ["shopping_list", "offline_access"]` — `offline_access` заставляет Claude
    запросить refresh token.
- **Protected Resource Metadata** — отдаёт SDK:
  - `resource` = URL MCP-сервера без завершающего `/`;
  - `authorization_servers` = [наш issuer];
  - `scopes_supported: ["shopping_list"]`.
- **Регистрация клиентов:**
  - **CIMD — основной способ.** `client_id`, являющийся HTTPS-URL, — это адрес документа клиента.
    AS загружает его и берёт `client_name`, `redirect_uris`. Загрузка:
    - только HTTPS, без приватных и loopback-адресов после резолва DNS;
    - лимит размера и таймаут;
    - `client_id` в документе совпадает с URL;
    - кэш в `oauth_clients` с учётом `Cache-Control`.
  - **DCR — запасной** (`POST /oauth/register`, JSON) для клиентов без CIMD.
- **`/oauth/authorize`:**
  - проверяет клиента, `redirect_uri`, PKCE S256, `resource`;
  - сохраняет запрос в `oauth_authorization_requests`;
  - перенаправляет в PWA на `/consent?request=<id>`.
- **Согласие — экран PWA** (спец. §8, п. 6):
  - вход, если нет сессии;
  - затем «Разрешить / Отклонить» с хостом адреса возврата и предупреждением для loopback.
  - Решение — `POST /api/oauth/consent`; бэкенд выдаёт код и возвращает URL редиректа
    с `code`, `state`, `iss`. Ошибки тоже возвращаются с `iss`.
- **`redirect_uri`** — точное совпадение с зарегистрированным; для `http://localhost` и
  `http://127.0.0.1` — без учёта порта (RFC 8252 §7.3, требование Claude Code).
- **`/oauth/token`:**
  - принимает `application/x-www-form-urlencoded`;
  - `authorization_code` — проверка PKCE, `resource` совпадает с кодом, код одноразовый;
  - `refresh_token`:
    - ротация — новый refresh в том же ответе, старый помечается `rotated_at`;
    - повтор старого refresh в течение **60 секунд** допустим и выдаёт новую пару — Claude
      обновляет и заранее, и по 401, запросы могут гоняться;
    - повтор позже → отзыв всей цепочки (`family_id`);
    - ошибка — `invalid_grant`;
  - ответ быстрее 10 секунд (лимит Claude).
- **`/oauth/revoke`** — отзыв refresh (со всей цепочкой) или access token.

### Токены и сессии

- **Все токены непрозрачные** — `secrets.token_urlsafe(32)` с префиксом:
  - `gl_pat_` — PAT;
  - `gl_at_` — access;
  - `gl_rt_` — refresh.

  В БД — только SHA-256. JWT не используем: единственный resource server — мы сами, отзыв должен
  работать сразу.
- **Сроки:** access token — 1 час, refresh — 30 дней, код авторизации — 5 минут,
  запрос согласия — 10 минут.
- **PWA — cookie-сессия:**
  - `HttpOnly; Secure; SameSite=Lax`;
  - в БД — хеш;
  - мутирующие запросы требуют `X-Device-Id` (спец. §9).
- **Пароли** — argon2 (`argon2-cffi`).
- **Ограничение попыток входа** — по IP и логину, в памяти процесса (процесс один, ADR-0001).
- **PAT** — показывается один раз, отзывается; имя PAT становится `client_name` источника.

### Границы модуля

- `auth` не зависит от `shopping_list_service`: он отвечает на вопрос «кто это», выставляет
  пользователя в контекст (ADR-0003) и строит источник.
- Эндпоинты `/oauth/*`, `/api/auth/*`, `/api/tokens`, `/api/oauth/*` — тонкие адаптеры над
  сервисом `auth` (ADR-0008).
- Задел под внешний IdP: способ входа — отдельная функция, создающая сессию; пароль не является
  обязательной частью модели входа в коде.

## Рассмотренные альтернативы

- **Встроенный AS `mcp` SDK** (`auth_server_provider=`) — нет CIMD, `iss`, `"none"`, сравнения
  loopback без порта. Документация SDK не рекомендует его для новых серверов.
- **FastMCP 4.x** — удобный `Depends()` и `MultiAuth`, но:
  - тот же встроенный AS;
  - три мажорные версии за год;
  - много зависимостей;
  - по собственным заметкам часть функций сломана на протоколе 2026-07-28.
- **Только DCR** — устарел в спецификации, ChatGPT и Claude предпочитают CIMD.
- **Отзыв цепочки при любом повторе refresh** — гонка обновлений в клиенте отключала бы
  пользователя.

## Последствия

- Собственный AS — самая объёмная и рискованная часть v1. Её покрывают интеграционные тесты,
  а на первом деплое — ручное подключение из claude.ai, Claude Code и ChatGPT (спец. §11).
- Обновление спецификации MCP затрагивает только наш модуль `auth`, а не библиотеку.
- CIMD означает исходящие запросы бэкенда к чужим URL — отсюда защита от SSRF.

## Как проверяется

- **Интеграционные тесты flow:**
  - CIMD и DCR: authorize → consent → token → refresh → revoke;
  - гонка двух refresh в окне — оба успешны;
  - повтор после окна — цепочка отозвана;
  - токен с чужим `resource` отклонён;
  - loopback-redirect с другим портом принят, с другим хостом — нет.
- **Тесты верификатора:** PAT, access token, отозванный, просроченный, с чужим `resource` →
  401 с `resource_metadata`.
- **Тесты загрузчика CIMD:** HTTP, приватный IP, слишком большой документ, несовпадение
  `client_id` — отказ.
- Тест: в таблицах токенов и сессий нет значений, совпадающих с выданными клиенту.
- Ruff `S` — запрет небезопасных генераторов случайных чисел.

## Уточнения реализации — 2026-10-04

- В миграции `0006` общее согласие выделено в `oauth_grants`: владелец, клиент, scope,
  resource, срок и отзыв семейства. Коды и пары токенов ссылаются на него через `family_id`.
  Блокировка строки семейства сериализует ротацию и отзыв всех его потомков.
- Replay, требующий отзыва, возвращает результат с ошибкой после коммита UoW;
  исключение внутри UoW откатило бы защитный отзыв вместе с транзакцией.
- Запрос согласия связан с отдельной `__Host-gl_oauth_<UUID>` HttpOnly/Secure cookie;
  первый просмотр под сессией связывает его с пользователем. UUID ссылки недостаточно
  для подтверждения из другого браузера или аккаунта.
- Refresh выдаётся только при `offline_access`. Срок семейства — абсолютные 30 дней
  от согласия, без продления при ротации; access ограничен оставшимся сроком семейства.
  Изменение scope требует нового согласия. Без offline_access семейство живёт один час.
- CIMD использует resolver aiohttp: проверяет все DNS-ответы и передаёт проверенные IP
  коннектору, сохраняя TLS-проверку имени. Загрузка не следует редиректам и не использует
  proxy из окружения или сжатие. Лимит тела 64 KiB, времени — по умолчанию 5 секунд.
- Минимальный экран `/consent` реализован на Vite/TypeScript в этапе 6; перенос в общий
  интерфейс PWA и экран управления подключениями остаются этапом 7.
- Ручной сценарий и состояние приёмки описаны в [OAuth](../oauth.md).
