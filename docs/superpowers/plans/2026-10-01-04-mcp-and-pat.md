# MCP-сервер и PAT — план реализации

Дата: 2026-10-01 · Статус: реализация завершена 2026-10-03.

**Цель:** добавить управление персональными токенами через cookie-защищённый REST API
и шесть MCP-инструментов из спеки §6.2, работающих через тот же сервис списка.
Результат проверяется локально без аккаунтов ассистентов и доступа к VPS.

**Основание:** спека §3.2, §4, §6.2, §9, §11; ADR-0001–0014, особенно
0003, 0004, 0008, 0010 и 0012. Исходное состояние — завершённый этап 3, `9050a27`.

## Приоритет и автономная работа

Владелец будет недоступен часть сессии. Задачи 1–7 выполняются последовательно автономно:
исследование установленного SDK, PAT, REST, MCP, тесты и документация. Обычные технические
решения принимает исполнитель и записывает в результатах. Не запрашивать реальные токены,
пароль пользователя, домен или вход в аккаунты для локальных тестов.

Подключение Claude Code к развёрнутому серверу и проверка Cloudflare относятся к этапу 5.
OAuth, claude.ai и ChatGPT — к этапу 6 и последующей приёмке; PWA и push — к этапам 7–8.
Эти проверки ведутся отдельно и не мешают локальному завершению этапа 4.
Если внешний доступ временно отсутствует, продолжать независимую работу, фиксируя конкретный
блокер. Не объявлять невыполненную проверку успешной.

## Исходные интерфейсы и ограничения

- `services/auth/context.py`: `acting_as(User)` сбрасывает ContextVar в `finally`.
- `services/auth/sessions.py`: `token_hash(str)` — SHA-256; переиспользовать для PAT.
- `db/session.py`: транзакциями управляет только `unit_of_work()`.
- `shopping_list_service`: все операции проверяют membership; default list требует ровно
  один доступный список. При нескольких списках необходимо явно передать UUID.
- `ItemUpdate.model_fields_set` различает пропуск поля и явный `null`. MCP обязан сохранить
  это различие, особенно для quantity, unit, note и tags=[].
- `update_item(id, data, source)` пока не принимает список: для MCP требуется проверять,
  что объект относится к выбранному списку, включая случай двух списков одного пользователя.
- `main.create_app()` собирает REST, lifespan конфигурирует БД и пароли.
  Экспорт OpenAPI вызывает фабрику без lifespan и без соединения с БД.
- Адаптеры не импортируют ORM/репозитории, нижние слои не импортируют MCP SDK.
- Отсутствие cookie не компенсируется PAT в REST; cookie не авторизует `/mcp`.
- PAT выдаётся как `gl_pat_` + `secrets.token_urlsafe(32)`, хранится только SHA-256.
  Имя PAT — `client_name`, UUID PAT — `client_id`, пользователь — subject.
- Результаты MCP используют существующие ItemRead/AddItemResult/TagUsageRead,
  quantities сериализуются числами, источники не раскрывают device/client IDs.

## Контракты этапа

### Управление PAT

| Маршрут | Вход | Успех | Защита |
|---|---|---|---|
| `GET /api/tokens` | — | 200, массив TokenRead | cookie |
| `POST /api/tokens` | `{name}` | 200, TokenIssued | cookie + X-Device-Id |
| `DELETE /api/tokens/{id}` | UUID | 204 | cookie + X-Device-Id |

`TokenRead`: id, name, created_at, last_used_at, revoked_at. `TokenIssued`: метаданные
и `token` (SecretStr, явная сериализация только в ответе выдачи). Сырой токен никогда
не входит в TokenRead, repr, событие списка или журнал. Имя очищается от пробелов по краям,
1–255 символов; extra поля запрещены. Повторяющиеся имена допустимы, различение — по UUID.
Список содержит активные и отозванные PAT пользователя, сортируется по created_at/id.
Отзыв своего уже отозванного PAT идемпотентен; чужой или неизвестный UUID — 404 с одинаковым
сообщением. Отозванный токен никогда не принимается. `Cache-Control: no-store` на ответах PAT.
Ошибки — существующий ErrorResponse; hint остаётся только в MCP.

Верификация PAT возвращает транспортно-независимую BearerIdentity Pydantic-схему
(user_id, client_id, client_name, scopes, resource). Проверяется существование пользователя;
scopes=[shopping_list], resource — канонный публичный `/mcp`. Не-PAT, неизвестный и
отозванный токен дают отказ. OAuth access tokens до этапа 6 отклоняются, без фиктивной
таблицы OAuth. `last_used_at` обновляется при успешной проверке токена и коммитится отдельной
короткой UoW верификатора; ошибка последующего инструмента не отменяет факт использования.
Не кешировать положительную верификацию между HTTP-запросами.

### MCP

Все инструменты принимают необязательный shopping_list_id. Опущенный UUID разрешается
через `get_default_shopping_list_id()`. Источник строится только из проверенной identity.

| Инструмент | Дополнительный вход | Результат | Аннотации |
|---|---|---|---|
| `get_shopping_list` | tag?, include_bought=false | ItemRead[] | readOnlyHint=true |
| `list_tags` | — | TagUsageRead[] | readOnlyHint=true |
| `add_items` | items: ItemCreate[], минимум 1 | AddItemResult[] | readOnlyHint=false, destructiveHint=false, idempotentHint=false |
| `update_item` | id, необязательные поля ItemUpdate | ItemRead | readOnlyHint=false, destructiveHint=true |
| `set_bought` | ids (минимум 1), bought | ItemRead[] | readOnlyHint=false, idempotentHint=true |
| `remove_items` | ровно одно из ids (непустое) / tag | `{count}` | readOnlyHint=false, destructiveHint=true |

Аннотации описывают семантику, не предоставляют доступ. Пустой PATCH допустим как в REST;
входы source/user_id/client_name запрещены. Не применять обычные Python default=None
так, чтобы пропущенные PATCH-поля стали явно переданными null: использовать поддержанный
SDK способ сохранения presence и проверить реальный tools/call.

Фильтр tag — нормализованное точное совпадение по §5.1/5.4, порядок позиций остаётся §5.7.
Добавить необязательный tag в `get_items`, сохранив прежнее поведение REST.
Добавить keyword-only `shopping_list_id: UUID | None = None` в сервис `update_item`:
проверить membership выбранного списка и соответствие item после получения lock;
несовпадение — ItemNotFoundError без изменений. REST без параметра сохраняет поведение.
Бизнес-проверки располагаются в сервисе, адаптер только собирает вызов.

Server instructions по-русски реализуют все пять правил спеки §6.2. Описания говорят
про объединение, явный null, выбор списка и удаление; клиенту не требуется знание REST.

- Все требования этапа 4 покрыты задачами: PAT/REST (2–3), верификатор/контекст (1, 4),
  шесть tools/instructions (5), транспорт/события/изоляция (6), проверка и документация (7).

## Результат выполнения — 2026-10-03

- Официальный `mcp` 2.2.0 добавлен в зависимости и lockfile; код реализован в текущем
  рабочем дереве. Миграция 0004 сгенерирована Alembic на временном Postgres и просмотрена.
- PAT: cookie-защищённые GET/POST/DELETE, SecretStr для выданного секрета, только SHA-256
  в БД, last_used_at, идемпотентный отзыв, owner isolation и no-store на успешных ответах.
- Все шесть tools, инструкции, аннотации, flat input с запретом extra/source,
  структурированные результаты, presence PATCH через публичный request_context.
- Resource validation и scope проверяются SDK; Host/Origin/CORS выводятся из public URL.
  Root metadata alias использует endpoint SDK и возвращает идентичный документ.
- Общая handler-обёртка переводит DomainError до перехвата SDK. Middleware проверяет
  обе формы error result: модель и сериализованный словарь `isError`. Это уточнение
  оформлено ADR-0016. Проверка только CallToolResult оказалась недостаточной:
  регрессионный real-commit тест воспроизвёл ошибочный commit, исправление проверено.
- Streamable HTTP: stateless + JSON response; modern discovery и legacy handshake
