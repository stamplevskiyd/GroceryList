# GroceryList — спецификация v1

Дата: 2026-09-29
Статус: черновик на ревью

## 1. Цель

PWA-приложение списка покупок с MCP-сервером. Когда пользователь обсуждает с LLM-ассистентом
(Claude, ChatGPT, Codex) готовку, ассистент сам добавляет недостающие ингредиенты в список.
Изменения моментально видны в приложении, на телефон приходит push-уведомление.

**Критерий успеха v1 (приёмочный сценарий):** пользователь пишет в claude.ai «хочу приготовить
карбонару» → Claude добавляет ингредиенты через MCP → в течение нескольких секунд на iPhone
приходит push, а в PWA появляются позиции с тегом «Для карбонары».

### Почему PWA

Не нужны Apple Developer аккаунт и переустановка приложения. Обновления доставляются деплоем.

### Контекст разработки

Владелец — backend Python-разработчик (Python, Postgres, Docker). Фронтенд строится по макету
Claude Design и проверяется ручными тестами по поведению, поэтому граница фронт/бэк должна быть
строгой и типизированной.

## 2. Решения (зафиксировано)

| Тема | Решение |
|---|---|
| Пользователи | v1 — один пользователь; модель данных сразу с `shopping_lists` + `shopping_list_members` (задел на семью) |
| Уведомления | v1 — только «список изменён другим источником». Механизм событий → outbox → Web Push общий, чтобы позже добавить уведомления «холодильника» и напоминания |
| MCP-клиенты | claude.ai (веб + мобильное приложение), ChatGPT — через OAuth 2.1; Claude Code, Claude Desktop, Codex CLI — через OAuth или персональный токен (PAT) |
| MCP-транспорт | Стандартный Streamable HTTP, один эндпоинт `/mcp` |
| MCP-библиотека | Официальный `mcp` Python SDK 2.x (`MCPServer`) в роли resource server; OAuth Authorization Server — собственные маршруты FastAPI (ADR-0010) |
| Вход | Собственный логин/пароль; бэкенд сам является OAuth Authorization Server. Слой auth проектируется так, чтобы позже добавить внешний IdP (Google/GitHub) |
| Офлайн | Не поддерживается. Service worker кэширует только оболочку приложения (нужен для установки PWA и push) |
| Организация списка | Свободные равноправные теги (отдел магазина, рецепт, что угодно) |
| Дубликаты | Объединение с суммированием количества |
| Купленное | Зачёркивается, уходит вниз; кнопка «Очистить купленное»; событие `item_bought` пишется в журнал (точка входа для «холодильника») |
| Бэкенд | Python, FastAPI, SQLAlchemy 2 (async), Alembic, Postgres |
| Фронтенд | React + TypeScript + Vite + vite-plugin-pwa; API-клиент генерируется из OpenAPI |
| Живые обновления | SSE |
| Push | Web Push (VAPID) через `pywebpush` |
| Инфраструктура | VPS (чистая), docker-compose: Caddy + backend + Postgres |

## 3. Архитектура

```
 claude.ai / ChatGPT ─┐  OAuth 2.1
 Claude Code / Codex ─┤  Bearer PAT        ┌──────────────── VPS (docker-compose) ────────────────┐
                      ▼                    │                                                      │
 iPhone (PWA) ──── HTTPS ───────────────►  │  Caddy ──► backend (FastAPI, один процесс)          │
   ▲                                       │   │  • /api/*          REST для PWA (cookie-сессия)  │
   │ Web Push (через push-сервис           │   │  • /api/events     SSE — живые обновления        │
   │ браузера)                             │   │  • /mcp            MCP Streamable HTTP           │
   │                                       │   │  • /oauth/*, /.well-known/*  OAuth-сервер        │
   └───────────────────────────────────────┤   │  • push-воркер (asyncio-задача в процессе)      │
                                           │   └─ статика фронтенда (собранный React)           │
                                           │                    │                                 │
                                           │               Postgres (volume + ежедневный pg_dump) │
                                           └──────────────────────────────────────────────────────┘
```

Весь бэкенд — один процесс: нагрузка ничтожная, отдельный воркер/Redis не оправданы.
Push-воркер при необходимости выносится в отдельный контейнер из того же образа.

### 3.1. Модули бэкенда

| Модуль | Ответственность | Зависит от |
|---|---|---|
| `domain/normalization` | Нормализация названий и единиц; чистые функции без БД | — |
| `domain/quick_add` | Разбор строки быстрого добавления («молоко 2 л» → название, количество, единица) по явной грамматике (§5.6); чистые функции без БД | `normalization` |
| `services/shopping_list_service` | Позиции, объединение, теги, «куплено», запись событий. **Единственное место бизнес-логики списка** | `db`, `normalization`, `events` |
| `services/events` | Запись события в `events` в той же транзакции + публикация в SSE-хаб и outbox | `db` |
| `services/auth` | Пароли, cookie-сессии, PAT, OAuth AS (authorize / token / register / revoke, metadata) | `db` |
| `api` | REST для PWA — тонкий слой над `shopping_list_service` | `domain`, `auth` |
| `mcp_server` | MCP-инструменты — тонкий слой над **тем же** `shopping_list_service` | `domain`, `auth` |
| `services/push` | Подписки, отправка, повторы, очистка мёртвых подписок | `events`, `db` |

REST и MCP — две «двери» к одной логике: поведение ручного ввода и ассистента не может разойтись.
Слои и полное дерево пакетов — ADR-0001 и ADR-0014.

### 3.2. Идентификация источника

Каждая мутация несёт `source`:
- `{kind: "app", device_id}` — `device_id` генерируется PWA при первом запуске и хранится локально;
  передаётся заголовком `X-Device-Id`.
- `{kind: "mcp", client_id, client_name}` — из OAuth-клиента или PAT (имя PAT задаёт пользователь).

Источник используется для push (не слать на устройство-источник) и для пометки «добавлено Claude» в UI.

## 4. Модель данных

Все таблицы имеют `id` (UUID) и `created_at`; где уместно — `updated_at`.

- **`users`**: `username` (уникальный), `password_hash` (argon2).
- **`shopping_lists`** (модель `ShoppingList`; «список покупок» — везде `shopping_list`, чтобы не путать с `list` Python): `name`, `owner_id`. В v1 создаётся автоматически при создании пользователя.
- **`shopping_list_members`**: `shopping_list_id`, `user_id`, `role` (`owner` / `editor`).
- **`items`**:
  - `shopping_list_id`, `name`, `name_normalized`
  - `quantity` — `numeric`, nullable (например, «соль» без количества)
  - `unit` — nullable, хранится в базовой форме (см. §5.2)
  - `note` — nullable
  - `is_bought`, `bought_at`
  - `sources` — `jsonb`, список уникальных источников в порядке появления:
    `[{"kind": "app"}, {"kind": "mcp", "client_name": "Claude"}]`. Новая позиция получает один
    источник; при объединении (§5.3) источник добавляется, если его ещё нет
- **`tags`**: `shopping_list_id`, `name`, `name_normalized`; уникальность `(shopping_list_id, name_normalized)`.
- **`item_tags`**: `item_id`, `tag_id`.
- **`events`**: `shopping_list_id`, `user_id`, `type`, `source jsonb`, `payload jsonb`.
  Типы v1: `items_added` (пачка, внутри — созданные и объединённые позиции), `item_updated`,
  `items_bought`, `items_unbought`, `items_deleted`, `bought_cleared`, `tag_renamed`, `tags_merged`,
  `tag_deleted`.
- **`push_subscriptions`**: `user_id`, `device_id`, `endpoint` (уникальный), `p256dh`, `auth`,
  `device_label`, `last_success_at`.
- **`notification_outbox`**: `event_id`, `subscription_id`, `status` (`pending` / `sent` / `failed`),
  `attempts`, `next_attempt_at`, `last_error`.
- **Auth**:
  - `sessions`: `user_id`, `token_hash`, `expires_at`, `device_id`
  - `personal_access_tokens`: `user_id`, `name`, `token_hash`, `last_used_at`, `revoked_at`
  - `oauth_clients`: `client_id`, типизированный JSONB `client_metadata` (имя, redirect URI,
    grant/response types), `registration_type` (`cimd` / `dcr`), `cache_expires_at`
  - `oauth_authorization_requests`: `client_pk`, типизированные параметры (включая PKCE и
    resource), `browser_token_hash`, `user_id`, `expires_at`, `consumed_at`
  - `oauth_grants`: одно согласие и семейство токенов — `client_pk`, `user_id`, `scope`,
    `resource`, `expires_at`, `revoked_at`; строка блокируется при ротации и отзыве
  - `oauth_codes`: `token_hash`, `family_id`, `code_challenge`, `redirect_uri`,
    `expires_at`, `consumed_at`
  - `oauth_tokens`: `access_token_hash`, необязательный `refresh_token_hash`, `family_id`,
    `expires_at` (access), `rotated_at`, `revoked_at` (только access).
    Общий срок и отзыв цепочки — в `oauth_grants`.

Все токены хранятся только в виде хешей; исходное значение показывается один раз.

## 5. Бизнес-правила

### 5.1. Нормализация названия

`name_normalized` = trim → схлопывание пробелов → нижний регистр → `ё`→`е`.
Отображается исходное `name` первой добавленной позиции.

### 5.2. Единицы

Поддерживаемые группы (синонимы → базовая единица):
- масса: `г`, `гр`, `кг` → `г`
- объём: `мл`, `л` → `мл`
- штуки: `шт`, `штук`, `штуки` → `шт`
- упаковки: `уп`, `упаковка`, `пачка` → `уп`

Неизвестная единица хранится как есть (после нормализации строки) и считается совместимой только
сама с собой. Для отображения количество в базовой единице приводится к удобной
(1500 г → 1,5 кг).

### 5.3. Объединение (merge)

При добавлении позиции ищется **некупленная** позиция в том же списке с тем же `name_normalized`
и той же базовой единицей (обе без единицы — тоже совпадение).

- Найдена → `quantity` суммируется; если количество задано только у одной стороны, берётся оно;
  если ни у одной — остаётся пустым. Теги объединяются. Заметки конкатенируются через `; `,
  если различаются. Источник добавления дописывается в `sources` (ручная позиция, в которую
  Claude добавил количество, помечается обоими источниками).
- Не найдена (включая случай, когда совпадающая позиция уже куплена) → создаётся новая позиция.
- Несовместимые единицы («лук 1 кг» и «лук 3 шт») → отдельные позиции.

### 5.4. Теги

- Свободные, равноправные, в рамках списка. Создаются неявно при назначении позиции.
- Тег без позиций не удаляется автоматически (остаётся для автодополнения); удаляется вручную.
- Переименование в имя уже существующего тега (сравнение по `name_normalized`) **объединяет теги**:
  позиции получают существующий тег, переименовываемый удаляется; событие `tags_merged`.
- Массовые действия по тегу: отметить все купленными, удалить все позиции с тегом.

### 5.5. Купленное

- Отметка → `is_bought=true`, `bought_at=now()`, событие `items_bought`.
- Снятие отметки → обратное, событие `items_unbought`.
- «Очистить купленное» → удаляет купленные позиции, событие `bought_cleared`
  (payload содержит удалённые позиции — история для будущего «холодильника»).

### 5.6. Быстрое добавление (разбор строки)

Отдельный механизм со своим модулем (`domain/quick_add`), эндпоинтом (`POST /api/items/quick-add`)
и набором тестов-примеров. Разбор выполняется только на сервере: единицы и синонимы живут в одном
месте (`domain/normalization`), фронтенд строку не разбирает.

Грамматика: `<название> [<количество> [<единица>]]`
- `количество` — число, дробная часть через `.` или `,`; стоит после названия, отделено пробелом.
- `единица` — любое слово после количества (можно слитно: `2л`); точка в конце отбрасывается
  (`шт.`). Известные синонимы приводятся к базовой единице с пересчётом количества (`1,5 кг` →
  1500 г), неизвестные сохраняются как есть (§5.2).
- Если строка не подходит под шаблон, вся она — название без количества.
- Название: первая буква приводится к верхнему регистру, остальное — как ввёл пользователь.

| Ввод | Название | Количество | Единица |
|---|---|---|---|
| `молоко 2 л` | Молоко | 2000 | мл |
| `яблоки 1,5 кг` | Яблоки | 1500 | г |
| `яйца 10` | Яйца | 10 | — |
| `батарейки АА 4 шт.` | Батарейки АА | 4 | шт |
| `соль` | Соль | — | — |
| `хлеб 1 буханка` | Хлеб | 1 | буханка |

Запрос несёт также `tags` — PWA передаёт теги, выбранные в фильтре на момент добавления. Дальше
позиция идёт через обычное `add_items` в `shopping_list_service` (то же правило объединения). Ответ содержит
результат разбора (`parsed`) и итог (`created` / `merged` + позиция), чтобы UI показал, что
распознано и что объединено.

### 5.7. Порядок позиций

- К покупке — `created_at desc` (новые сверху; объединение порядок не меняет).
- Купленные — `bought_at desc`.
- Фильтрация по тегам в PWA — на клиенте по полному списку (множественный выбор, логика «ИЛИ»).

## 6. API

### 6.1. REST (для PWA)

Аутентификация — cookie-сессия (`HttpOnly`, `Secure`, `SameSite=Lax`). Схема — OpenAPI,
из неё генерируется TypeScript-клиент.

- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/me`
- `GET /api/health` — публичный: `{status, version}`, проверка БД (деплой и healthcheck, ADR-0015)
- `GET /api/items?include_bought=` — позиции (весь список; фильтр по тегам — на клиенте, §5.7)
- `POST /api/items` — пакетное добавление структурированных позиций (то же правило merge)
- `POST /api/items/quick-add` — `{text, tags}`: разбор строки на сервере + добавление (§5.6)
- `PATCH /api/items/{id}`, `DELETE /api/items/{id}`
- `POST /api/items/bought` — `{ids, bought}`
- `POST /api/items/clear-bought`
- `GET /api/tags`, `PATCH /api/tags/{id}` (переименование), `DELETE /api/tags/{id}`
- `POST /api/tags/{id}/bulk` — `{action: "mark_bought" | "delete_items"}`
- `GET /api/events` — SSE-поток
- `GET/POST/DELETE /api/push/subscriptions`, `GET /api/push/vapid-public-key`
- `GET/POST/DELETE /api/tokens` — PAT
- `GET/DELETE /api/oauth/grants` — подключённые приложения

Публичная регистрация добавлена по решению владельца 2026-10-04: логин и пароль,
автоматический вход, новый личный список «Покупки». Повтор занятого логина — конфликт;
частые попытки ограничиваются. CLI `python -m grocery create-user` остаётся доступен.

### 6.2. MCP

Эндпоинт `/mcp`, Streamable HTTP. Принимает `Authorization: Bearer <token>`, где токен — OAuth
access token или PAT. OAuth — по спецификации авторизации MCP 2026-07-28: Authorization Code +
PKCE S256, регистрация клиентов через Client ID Metadata Documents (основной способ) и Dynamic
Client Registration (запасной), `resource` (RFC 8707) с проверкой аудитории токена, `iss` в ответе
авторизации (RFC 9207), `/.well-known/oauth-authorization-server` и
`/.well-known/oauth-protected-resource`. Детали — ADR-0010.

| Инструмент | Аргументы | Результат | Аннотации |
|---|---|---|---|
| `get_shopping_list` | `shopping_list_id?`, `tag?`, `include_bought=false` | позиции: id, name, quantity, unit, tags, is_bought | read-only |
| `list_tags` | — | теги с числом позиций | read-only |
| `add_items` | `items: [{name, quantity?, unit?, tags?, note?}]` | по каждой: `created` / `merged` + итоговая позиция | — |
| `update_item` | `id`, `name?`, `quantity?`, `unit?`, `tags?`, `note?` | позиция | — |
| `set_bought` | `ids`, `bought` | обновлённые позиции | idempotent |
| `remove_items` | `ids?` или `tag?` | число удалённых | destructive |

Все инструменты принимают необязательный `shopping_list_id`; если он не передан, используется
единственный список пользователя (ADR-0003).

**Инструкции сервера (MCP `instructions`)** — суть:
1. Перед добавлением вызвать `get_shopping_list` и `list_tags`; переиспользовать существующие названия и теги.
2. Названия — на языке пользователя, в единственном базовом виде («лук», не «луковицы»).
3. Для ингредиентов рецепта ставить тег «Для <рецепт>»; тег отдела — из уже существующих тегов,
   если подходит.
4. Не добавлять то, что обычно есть дома (соль, вода, масло), не спросив пользователя.
5. После добавления кратко сообщить, что добавлено и что объединено.

Ошибки инструментов возвращаются как MCP tool errors с понятным текстом и подсказкой для модели
(не найдено, неверная единица, пустой список позиций) — ADR-0012.

## 7. Живые обновления и уведомления

1. Мутация в `shopping_list_service` в одной транзакции пишет данные, **одно** событие и строки outbox
   (по одной на каждую подписку, кроме подписок устройства-источника).
2. После коммита событие публикуется во внутренний SSE-хаб → открытые PWA обновляются.
3. Push-воркер (asyncio-задача) выбирает `pending`-строки outbox, отправляет через `pywebpush`.
   - Успех → `sent`, обновить `last_success_at`.
   - `404` / `410` → удалить подписку.
   - Прочие ошибки → повтор с экспоненциальной задержкой, до 5 попыток, затем `failed`.
4. Текст уведомления формируется из события, пример:
   «Claude добавил 7 позиций: лук, морковь, свёкла и ещё 4». Один вызов инструмента = одно
   уведомление.

SSE: встроенный `EventSourceResponse` FastAPI (ADR-0009), heartbeat каждые 15 секунд — FastAPI шлёт его сам
(нужен в том числе из-за Cloudflare-прокси перед хостом).
При переподключении PWA перезагружает список целиком — пропущенные события не важны.

Уведомления v1 шлются на события с источником `mcp` и на события `app` с другого устройства.

## 8. Экраны (ТЗ для Claude Design)

Mobile-first (iPhone), светлая и тёмная темы; на десктопе та же раскладка, шире. Язык интерфейса —
русский.

**Макет готов:** [`docs/design/`](../../design/README.md) — экраны (`screens/*.dc.html`), токены
(`tokens.css`) и соответствие экранов пунктам ниже.

1. **Вход** — логин, пароль, кнопка «Войти», сообщение об ошибке.
2. **Список (главный экран)**
   - Поле быстрого добавления сверху или снизу (удобно большим пальцем). Строка уходит
     на сервер как есть (§5.6); новая позиция получает теги, выбранные в фильтре.
   - Горизонтальная лента чипов-тегов для фильтрации (множественный выбор).
   - Переключатель вида: «Списком» / «По тегам». В режиме «По тегам» позиция с несколькими тегами
     показывается в каждой своей группе (это одна запись: отметка синхронна); позиции без тегов —
     в группе «Без тега».
   - Строка позиции: чекбокс, название, количество с единицей, чипы тегов, метки источников
     из `sources`: «добавил Claude» (или имя другого MCP-клиента). Если у позиции несколько
     источников (объединение), показываются все метки; ручной источник помечается «вы» только
     в сочетании с другими.
   - Купленные — зачёркнуты, в свёрнутом блоке внизу; кнопка «Очистить купленное».
   - Пустое состояние (список пуст — подсказка «попросите Claude…»).
   - Живое появление новых позиций (лёгкая анимация/подсветка).
3. **Карточка позиции** (bottom sheet) — название, количество, единица (выбор из списка + своя),
   теги с автодополнением, заметка, «Удалить».
4. **Теги** — список тегов с числом позиций; переименовать, удалить; массовые действия
   «Отметить все купленными», «Удалить все позиции с тегом» (с подтверждением).
5. **Настройки**
   - Уведомления: включить/выключить на этом устройстве, список устройств с возможностью удалить.
   - Персональные токены: создать (имя → токен показывается один раз с кнопкой «Скопировать»),
     список, отозвать.
   - Подключённые приложения (OAuth): имя клиента, дата подключения, «Отключить».
   - «Как подключить ассистента»: URL MCP-сервера, короткие инструкции для claude.ai, ChatGPT,
     Claude Code, Codex.
   - Выйти.
6. **Экран согласия OAuth** (маршрут PWA `/consent`, открывается в браузере при подключении
   коннектора) — форма входа, если не залогинен; затем «<Клиент> запрашивает доступ к вашему списку
   покупок», хост адреса возврата (для `localhost` / `127.0.0.1` — предупреждение, что это приложение
   на этом компьютере), «Разрешить» / «Отклонить».
7. **Онбординг установки на iOS** — если приложение открыто в Safari, а не установлено:
   «Поделиться → На экран „Домой“», пояснение, что без этого не будет уведомлений.

## 9. Безопасность

- HTTPS обязателен (Caddy / Cloudflare).
- Пароли — argon2; ограничение частоты попыток входа (по IP и логину).
- Cookie: `HttpOnly`, `Secure`, `SameSite=Lax`; мутирующие REST-запросы требуют заголовок
  `X-Device-Id` (дополнительно к SameSite защищает от CSRF простых форм).
- OAuth: только Authorization Code + PKCE (S256); `redirect_uri` — точное совпадение
  с зарегистрированным (для loopback-адресов — без учёта порта); access token живёт 1 час,
  refresh token — 30 дней с ротацией (окно повтора 60 секунд, затем отзыв всей цепочки);
  токен принимается только с `resource`, равным URL нашего MCP-сервера.
- Загрузка CIMD-документов — с защитой от SSRF (только HTTPS, без приватных адресов, лимиты
  размера и времени) и кэшем.
- Все токены хранятся как хеши (SHA-256), PAT и refresh отзываются.
- Postgres не публикуется наружу; наружу открыты только 80/443 Caddy.
- Секреты (VAPID-ключи, секрет сессий) — через `.env`, не в репозитории.

## 10. Инфраструктура и деплой

- **`docker-compose.yml`** (в корне репозитория, как и `Caddyfile` и Dockerfile'ы — ADR-0014): `caddy`, `backend`, `postgres`, `backup` (ежедневный `pg_dump` в volume,
  хранение N последних копий).
- Образ `backend` — Python, только API/MCP/OAuth.
- Образ `caddy` — multi-stage: сборка фронтенда (Node) → официальный образ Caddy со статикой
  и Caddyfile. Caddy раздаёт статику и проксирует `/api`, `/mcp`, `/oauth`, `/.well-known`
  на `backend`.
- Миграции Alembic (с `downgrade`) применяются при старте `backend`; образ Postgres — `postgres:18-alpine`.
- **CI/CD** (ADR-0015): GitHub Actions — проверки на каждый push, образы на Docker Hub
  (`grocerylist-backend`, `grocerylist-caddy`) для `main` и тегов, деплой на VPS кнопкой или
  по тегу `v*` с бэкапом перед миграциями и проверкой `/api/health`. VPS ничего не собирает.
- **Адрес** задаётся конфигом (`APP_PUBLIC_URL`, домен в `Caddyfile`):
  - разработка — `localhost`;
  - старт продакшена — технический адрес хостинга `s157254.love-is.nexus`
    (резолвится в IP Cloudflare — трафик идёт через прокси хостинга; на первом деплое
    проверить HTTPS, SSE и подключение MCP-коннектора);
  - запасные варианты — `<IP>.sslip.io` (прямое подключение, сертификат выпускает Caddy)
    или собственный домен.
  - Смена адреса требует переподписки на push и переподключения коннекторов — переехать
    до начала регулярного использования.

## 11. Тестирование

- **Бэкенд** (pytest):
  - `domain/normalization` — юнит-тесты (нормализация, конвертация, совместимость).
  - `shopping_list_service` — на реальном Postgres (testcontainers): merge, теги, купленное, события, outbox.
  - REST — через `httpx.AsyncClient`.
  - MCP — через клиент из SDK внутри процесса: каждый инструмент, аутентификация PAT и OAuth.
  - OAuth — интеграционные тесты полного flow для CIMD и DCR (authorize → consent → token →
    refresh → revoke), включая гонку двух refresh и повтор после окна.
  - Push — отправка замокана; проверка outbox, повторов, удаления подписок на 410.
- **Фронтенд** — ручные сценарии (чек-лист в плане реализации); позже — Playwright smoke.
- **Приёмка** — сценарий из §1 на реальном iPhone и claude.ai; дополнительно — подключение из
  Claude Code по PAT и из ChatGPT по OAuth.

## 12. Вне v1

- «Холодильник» (запасы, сроки годности, предложения рецептов/покупок) — данные копятся в `events`.
- Напоминания по расписанию.
- UI совместного доступа (приглашения, несколько участников).
- Офлайн-режим.
- Вход через внешний IdP (Google/GitHub).
- Несколько списков в UI.
