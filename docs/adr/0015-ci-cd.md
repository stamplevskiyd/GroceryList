# ADR-0015. CI/CD: GitHub Actions, образы на Docker Hub, деплой кнопкой и по тегам

Статус: принято · Дата: 2026-09-29

## Контекст

Код — на GitHub (`stamplevskiyd/GroceryList`). Прод — слабый VPS с docker-compose (спец. §10).
Сборка фронтенда (Node + Vite) на VPS может не уложиться в память, поэтому образы собираются
в CI, а VPS только скачивает и запускает их. Проверки уже собраны в `scripts/check.sh` (ADR-0007).

## Решение

### Реестр — Docker Hub, публичные репозитории

- `stamplevskiyd/grocerylist-backend` и `stamplevskiyd/grocerylist-caddy`.
- Образы не содержат секретов: всё секретное — в `.env` на VPS (ADR-0006). Публичность означает
  только, что собранный код можно скачать.
- Теги образов: **короткий SHA коммита** всегда; **версия** (`v0.3.0`) — для git-тегов.
  Тег `latest` не используется: на VPS всегда явно указано, какая версия запущена.
- Платформа — `linux/amd64` (архитектура VPS); меняется одной строкой в workflow.

### Workflows — `.github/workflows/`

| Workflow | Когда | Что делает |
|---|---|---|
| `ci.yml` | каждый push и pull request | `scripts/check.sh`: lint, типы, тесты (Docker на раннере есть — testcontainers работает), актуальность OpenAPI-контракта. Кэш uv и npm |
| `images.yml` | зелёный `ci.yml` на `main` и на тегах `v*` | Сборка `backend.Dockerfile` и `caddy.Dockerfile` (buildx, кэш слоёв в GitHub Actions), push на Docker Hub с тегами SHA (+ версия для git-тега) |
| `deploy.yml` | **вручную** (`workflow_dispatch`, вход — тег образа: SHA или версия) и **автоматически** после `images.yml` для тегов `v*` | Деплой на VPS через `scripts/deploy.sh` |

- Push в `main` без тега собирает образы, но не деплоит: прод меняется только осознанно —
  кнопкой или релизным тегом.
- `deploy.yml` работает в GitHub environment `production`: секреты VPS доступны только ему,
  параллельные деплои запрещены (`concurrency`).

### Деплой — `scripts/deploy.sh <tag>`

Команды деплоя — в скрипте (как и остальные, ADR-0007); workflow только вызывает его. Этот же
скрипт можно запустить с ноутбука, если GitHub недоступен.

1. Копирует на VPS `docker-compose.yml` (по SSH, в каталог приложения) — конфигурация всегда
   соответствует версии кода. `Caddyfile` зашит в образ `caddy`.
2. Записывает `IMAGE_TAG=<tag>` в `deploy.env` на VPS (отдельно от `.env` с секретами).
3. `docker compose pull`.
4. **Бэкап перед миграциями**: `pg_dump` в том же volume, что и ежедневные бэкапы, с префиксом
   `pre-deploy-<tag>-<время>`; хранятся N последних.
5. `docker compose up -d` — `backend` применяет миграции при старте (спец. §10).
6. **Проверка**: ждёт, пока `GET /api/health` отдаст `200` с `version == <tag>`; иначе — деплой
   помечается упавшим, в логе — команда отката.
7. `docker image prune` — удаляет старые образы (место на VPS).

**Откат** — тот же `deploy.yml` с предыдущим тегом. Если новая версия успела применить
миграцию, сначала `alembic downgrade` (ADR-0013) или восстановление из `pre-deploy`-бэкапа.

### `docker-compose.yml`

Один файл для разработки и прода:

```yaml
backend:
  image: ${DOCKERHUB_USER}/grocerylist-backend:${IMAGE_TAG:-dev}
  build: { context: ., dockerfile: backend.Dockerfile }
```

- Локально `docker compose up --build` собирает образы с тегом `dev`.
- На VPS `pull` + `up -d` без сборки.

### `GET /api/health`

Публичный эндпоинт (без аутентификации, ADR-0003):

- ответ — `{status, version}`;
- `version` берётся из build-arg `APP_VERSION`, зашитого в образ;
- проверяет соединение с БД (`SELECT 1`).

Используется деплоем и healthcheck'ом docker-compose.

### Секреты

- **GitHub Secrets:** `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN` (access token с правом записи —
  только для `images.yml`).
- **Environment `production`:** `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY` (ключ отдельного
  пользователя `deploy`), `VPS_KNOWN_HOSTS` (закреплённый ключ хоста — без
  `StrictHostKeyChecking=no`).
- **VPS:** `.env` с секретами приложения создаётся руками при подготовке и в CI не попадает.
  Для скачивания публичных образов логин на Docker Hub не нужен.

### Подготовка VPS — чек-лист в `README.md`

Выполняется руками один раз:

- Docker Engine + compose plugin;
- пользователь `deploy` в группе `docker`, вход только по ключу;
- файрвол: открыты 22, 80, 443;
- каталог приложения с `.env` (по `.env.example`);
- проверка, что `APP_PUBLIC_URL` резолвится на VPS (или на прокси хостинга — спец. §10).

## Рассмотренные альтернативы

- **Сборка на VPS** (`git pull && docker compose up --build`) — сборка фронтенда может не
  поместиться в память слабого VPS; в прод попадает не то, что проверено в CI.
- **GHCR** — для приватных пакетов на бесплатном плане 1 ГБ исходящего трафика в месяц, то есть
  4–5 деплоев.
- **Один приватный репозиторий Docker Hub** с тегами `backend-*` / `caddy-*` — укладывается
  в лимит одного приватного репозитория, но код в образах скрывать не нужно.
- **Автодеплой каждого push в `main`** — любой коммит, включая документацию, менял бы прод.

## Последствия

- Релиз — `git tag v0.x.y && git push --tags`: CI → образы → деплой без ручных шагов.
- Горячий деплой конкретного коммита из `main` — кнопкой с его SHA.
- Лимит pull'ов Docker Hub (100 за 6 часов без логина) при наших объёмах не достигается.

## Как проверяется

### Уточнения реализации — 2026-10-04

- Связи CI → images → deploy реализованы через `needs` и reusable workflows
  (`workflow_call`), чтобы сохранять точный контекст push/тега. Ручной `workflow_dispatch`
  остаётся в `deploy.yml`. PR не вызывает сборку с registry secrets.
- Короткий SHA — 12 символов. Релизный образ и SHA-образ собираются с соответствующим
  `APP_VERSION`; версия берётся из файла внутри образа, а не из runtime `.env`.
- Конфигурации хранятся в отдельных каталогах релизов, имя Compose-проекта фиксировано.
  `current` указывает последнюю попытку запуска, `last-successful` — подтверждённый релиз.
  В дополнение к GitHub concurrency сервер защищён `flock`.
- До миграций проверяются revision/version OCI-меток обоих образов. После старта
  проверяется публичный HTTPS health, а не только локальный адрес контейнера.
- `prune` касается только dangling images старше суток. Откат и восстановление БД —
  явные операторские действия по [инструкции](../deployment.md).

### Проверки

- `ci.yml` — обязательная проверка для `main` (branch protection, когда появятся PR).
- Деплой считается успешным только после `/api/health` с ожидаемой версией.
- `scripts/deploy.sh` проверяется `shellcheck` в `scripts/lint.sh`.
